## 2. Кто атакует (threat actors)

| # | Кто | Capability | Мотивация |
|---|---|---|---|
| T1 | **Pasive network attacker** | Sniff ws / tcp on the wire | Steal plaintext, build social graph |
| T2 | **Active network MITM** | Insert/modify packets, hijack TLS | Impersonate, replay, downgrade |
| T3 | **Compromised operator** (rogue admin или DB dump) | Full DB read + write, full server logs | Read message bodies (T3a), build social graph (T3b), inject fake messages (T3c) |
| T4 | **Compromised Apple / Google** (push provider) | Read all push payloads, can drop | Surveillance, denial-of-service |
| T5 | **Stolen unlocked device** | Full read of app sandbox files (`sinhron.db`, `sinhron-mls.sqlite`) | Read history + impersonate next |
| T6 | **Stolen LOCKED device + forensic tools** | Cold-boot attack, jailbreak, brute-force iOS sandbox isolation | Read history, possibly impersonate |
| T7 | **Malicious peer in same chat** | Has MLS membership, sees plaintext | Send abuse, leak content out-of-band |
| T8 | **Off-path attacker** (compromised public CA) | Issue fraudulent TLS cert for operator domain | MITM TLS |
| T9 | **Operator infrastructure compromise** (root on VM) | Read .p8 APNs key, JWT secrets, db credentials | Spoof identity, decrypt push tokens, full DOS |
| T10 | **State-level adversary** | Subpoena operator, network observation at scale, exploit broker | **Out of scope for Sinhron v1** |

## 3. Mitigations по каждой угрозе

### T1 — Passive sniffer

**Защита.**
- TLS на всех transport'ах. WS over `wss://`, HTTP over `https://`. TLS pinning (T1.5 уже спека упоминает; mechanism у нас — WU B3, `TlsPinning` struct) когда operator deploy с pinned CA.
- MLS payload — все application messages зашифрованы AES-128-GCM с ratcheting keys. Sniffer видит ciphertext + metadata (timing, sizes, peer-pair).

**Остаточный leak.**
- Metadata: traffic-analysis (когда вы говорите с кем) → mitigated по timing, не по identity (TLS hides target).
- Размеры сообщений (`ciphertext.len()`) — с 2026-10-13 MLS app messages паддятся до кратного 512 Б (§5 #5), так что видна длина с точностью до бакета; размеры медиа-блобов не паддятся (§5 #13, tech-debt 2.19).

**Код.** `sinhron_net::client::handshake`, `tokio_tungstenite::connect_async_tls_with_config` (use_preconfigured_tls).

### T2 — Active MITM

**Защита.**
- TLS pinning (WU B3) — клиент отказывает любому certificate chain не оканчивающемуся на bundled operator CA. Compromised public CA не помогает.
- MLS handshake verifies group epoch transcripts; injected Welcome не пройдёт validation.
- Action proofs binding: подписи включают `domain_prefix || sha256(body) || ts`. Replay одного действия как другое — невозможно (Risk #2 pairwise-non-prefix invariant).
- Привязка к серверу (ADR-086, 2026-11-04, `docs/security-review-2026-11.md` mls-identity:5, server-http:8): всё, что проверяет сервер — вход по WS, подтверждения действий, регистрация, — подписано как `sinhron-server-host-v1:` ‖ имя сервера ‖ 0 ‖ сообщение; имя берётся из адреса сервера в приложении (не IP запасного DNS), сервер принимает только свои имена (`SINHRON_PUBLIC_HOSTNAME`). Подпись, сделанную для другого сервера, нельзя переслать сюда; подписи старого вида не принимаются (переходного периода нет — сервер и телефоны обновляются вместе).

- Подмена DNS (провайдер, роутер, 2026-10-22; ADR-072): чужой адрес для нашего хоста не принимается — TLS проверяет сертификат на наше имя. Чтобы при этом связь была, адрес **проверяется** (TLS-рукопожатие к нему с нашим именем) и при неудаче берётся из DNS-over-HTTPS (1.1.1.1 / 8.8.8.8) или из памяти; проверка сертификата на всех путях прежняя — сменить адрес можно, ослабить проверку нельзя.

**Код.** `sinhron_net::tls::TlsPinning`, `sinhron_net::dns` (проверка адреса, DoH), `server::handlers::proof::verify_action_proof`.

### T3 — Compromised operator (наиболее интересный сценарий)

**T3a (read message bodies):** МLS application messages шифруются ключами, которых сервер никогда не видит. Server stores **ciphertext only** (`messages.ciphertext: bytea`). Даже если оператор дампит всю Postgres БД — он не может расшифровать.

**T3b (social graph):** Server NEEDS to route fanout, поэтому хранит `group_members(group_id, device_pk)`. Этот граф **виден** оператору. Mitigation: sealed sender (ADR-023, 2026-10-13) — для запечатанных сообщений сервер не знает группу (конверт HPKE на ключ доставки получателя, `group_id` пуст, в `messages` ничего). Остаётся видно: какое аутентифицированное соединение отправило конверт и кому он; состав групп всё ещё хранится для обычных `Submit` и звонков. Ключи доступа на собеседника (ADR-071) графа не добавляют: в `access_keys` — только хэши без имён (их число ≈ число собеседников, число отозванных ≈ число заблокированных), ключ на WS-пути нарочно не передаётся.

**T3c (inject fake messages):** Server должен подписать никем. Каждый MLS message includes sender's MLS signature; receiver MLS group verify rejects forged. Server **не имеет** sender's private key (only DerivedIdentity holder does).

**Остаточный leak.**
- Server знает: кто кому когда (метаданные fanout)
- Server знает: размеры сообщений
- Server знает: per-recipient delivery times
- Документировано в спеке §13.1.
- Аудит 2026-11b (2026-11-12): _закрыто (ADR-100)_ — сервер в одиночку подсовывал телефону, восстановленному из копии, свою карточку чата и читал его переписку (01/CM-01); карточка принимается только с подписью моего другого устройства. Старая настоящая карточка заодно с удалённым участником (01/CM-02) — закрыто частично, см. §5 п. 26. _Закрыто (ADR-101)_ — потерянный ответ на Commit больше не выбивает устройство из чата молча (01/CM-03, 09/CN-30). **Открыто — «доставлено» ≠ дошло:** сервер помечает сообщение и приглашение доставленным, когда кладёт их в очередь соединения (04/WS-02, 04/WS-12; 02/metadata-received-means-queued — не перепроверена); обрыв в этот момент = потеря без следа, в чате с коротким таймером сообщение может исчезнуть непрочитанным. Заявлено аудитом, ждёт проверки: номер и время сообщения задаёт сервер (02/crypto-message-id-not-in-envelope, CM-14) — правки, удаления, реакции и «прочитано» теоретически можно перенаправить на другое сообщение.

**Код.** `server::ws::handle_submit` — никогда не пытается decrypt; `sinhron_sync::group::process_incoming` — MLS verifies sender.

### T4 — Compromised push provider (Apple, Google)

**Защита.**
- Push payload (ADR-038, 2026-10-16 — настоящий APNs): server отправляет **NO plaintext** — только «Новое сообщение» / «New message» (язык телефона) и бейдж, без `group_id` (TD 2.7), с одним `apns-collapse-id` (не видно и числа сообщений). **ADR-056 (2026-10-18):** к срочной запечатанной доставке отправитель прикладывает превью (вид, начало текста, чат, подпись), HPKE на ключ доставки получателя, всегда 689 байт; сервер кладёт его в push как есть (`p`, `mutable-content`), без схлопывания; Notification Service Extension вскрывает его на телефоне (CryptoKit) и пишет имя и текст. VoIP-push несёт `h` = HMAC(ключ телефона, call id ‖ group id) — новое значение на каждый звонок. Будят только доставки, которые отправитель пометил «срочными» (настоящее сообщение) — сервер теперь отличает их от служебных (квитанции, «печатает») — новая метаинформация.

**Остаточный leak.**
- Apple знает: ваш device + ~timestamp + размер encrypted payload (превью — всегда одного размера); с превью — что уведомление «изменяемое» и сколько их (схлопывания больше нет)
- Не знает: кто вам пишет, что пишет, в какую группу; по меткам звонков — не связывает звонки одного чата (метка своя на каждый звонок и на каждый телефон)
- **Google (ADR-057, Android с FCM, 2026-10-18)** знает: на этом телефоне (и в его Google-аккаунте) стоит Sinhron, проект Firebase этого сервера, токен телефона и **время каждого push**. Не знает: что пришло, от кого, в какой чат, сообщение это или звонок, сколько непрочитанных — в data-сообщении одно поле `s`: JSON, дополненная до 128 байт и запечатанная AES-256-GCM ключом телефона (32 байта, сделал телефон, лежит в его SharedPreferences, бэкап выключен); сообщение и звонок одного размера, приоритета и TTL, без collapse key. Подделать push Google не может так, чтобы телефон его принял (AEAD с ключом телефона), но может не доставить (DoS) или повторить старый (звонок старше 2 минут телефон отбрасывает; повтор сообщения — лишнее пробуждение). Ключ сервисного аккаунта (`/etc/sinhron/fcm/service-account.json`) — как `.p8` APNs: с ним можно слать push всем телефонам этого сервера (но телефон отбросит то, что не запечатано его ключом). id Firebase в `GET /v1/push/info` публичны (они в любом APK с Firebase): с ними можно лишь получить свой токен, не слать.
- Сервер (ADR-056) дополнительно знает: у каких доставок есть превью; ключ меток звонков телефона (он и так знает группу звонка) — не узнаёт имён, текста, блокировок. **Подмена ключа доставки (ADR-082, запись 236):** до неё сервер мог отдать отправителю свой ключ вместо ключа получателя и прочитать превью (кто, чат, до 320 байт текста). Теперь ключ подписан хозяином, превью кладётся только на подписанный; на неподписанный (старое приложение собеседника, старый сервер — или подмена) сообщение уходит без превью («Новое сообщение»). Остаётся: подставив неподписанный ключ, сервер узнаёт чат этого сообщения (как без sealed sender); текст — нет
- Телефон: закрытые ключи доставки (недели −2…+2), имена чатов и людей, список заблокированных — в Keychain-группе `com.sinhron.shared`, общей только с нашим расширением («после первой разблокировки, только это устройство»); ключ устройства (ADR-021) — в группе самого приложения, расширению недоступен

**Код.** `server::apns::alert_body(unread, lang, preview)` — в теле только `aps` и запечатанное `p` (тесты `the_alert_carries_no_content`, `a_sealed_preview_rides_along_for_the_extension`); `server::push::notify_offline`, `call_hint`; клиент — `sinhron_sync::push_preview`, `ios/Shared/PushShared.swift`, `ios/NotificationService`. Ключ .p8 — файл uid 10001 / 400 на хосте, в git и логах никогда.

**Защита.**
- Local SQLite зашифрованы SQLCipher (T1.1) ключом из BIP-39 phrase
- iOS Data Protection класса `completeUntilFirstUserAuthentication` на всех папках приложения (ADR-021, tech-debt 2.6 закрыт)
- Ключ устройства в Keychain (ADR-021) открывает базу без фразы — поэтому разблокированный телефон = доступ к чатам; барьер — код телефона и «Блокировка приложения» (Face ID)
- Запись 229 (`docs/security-review-2026-11.md`, storage-devices:3, :5, :6, :4): «Подключить новое устройство» и «Записать слова» в Настройках всегда спрашивают Face ID / код телефона — включена «Блокировка приложения» или нет (`confirmOwner`, `app_lock.dart`); без кода у телефона спрашивать нечем — идёт дальше. Время «блокировать снова» считается и по часам телефона, и по времени с запуска (`Stopwatch`), часы назад — блокирует: перевод часов в Настройках блокировку не обходит. - Phrase derivation детерминирована, но требует knowledge of phrase

**Остаточный leak.**
- Если устройство **разлочено** и app открыт — attacker reads RAM via debugger / lldb. Mitigated by iOS sandboxing (no jailbreak required) and zeroize-after-use (Risk #6).
- Если app закрыт, а устройство залочено после перезагрузки → Keychain и файлы недоступны до первого ввода кода (класс `AfterFirstUnlock`).
- Аудит 2026-11b (2026-11-12, открыто): Android — звонок открывает приложение поверх экрана блокировки, пока идёт звонок, чаты и настройки доступны без кода телефона (06/LOCK-3 = 08/FFI-and-push-1); если чаты не открылись при запуске, приложение предлагает «создать аккаунт» и затирает ключ старого (06/KEYS-1; I17 — про базу, ключ в него не входит); заплатки для LOCK-3 и KEYS-1 готовы, в 0.12.0 не применены — ждут решения владельца и проверки на телефоне. _Закрыто 2026-11-12 (выпуск 0.12.0, запись 257):_ 24 слова из связки ключей — только после Face ID/кода (06/SEED-1); «Удалить аккаунт», «Выйти», «Отключить устройство», выключение блокировки и смена таймаута — только после Face ID/кода (06/LOCK-6, DEV-7, LOCK-8); клавиатура под закрытой блокировкой не печатает (LOCK-1); запуск без экрана не выключает блокировку (LOCK-4). На телефонах не проверено. Заявлено аудитом, ждёт проверки (черновики, оценки от низкой до средней): вредное приложение на том же Android — экспортированная `MainActivity` принимает «Ответить» от любого приложения (07/APP-links-1 = 05/CALL-dartcontrol-2 = 08/FFI-and-surface-2 = 08/FFI-and-push-2); до ключей и базы оно не достаёт.

**Код.** `apply_encryption_key` в sinhron_storage + sinhron_sync provider.

### T6 — Stolen locked device + forensic tools

**Защита.**
- SQLCipher AES-256 by-the-book; brute-force resistance того же порядка как Signal / WhatsApp DB encryption.
- Если у attacker'а есть BIP-39 phrase — game over (recovery design). Mitigation: phrase никогда не отправляется на сервер; из буфера обмена стирается через 60 с (CRIT-1.3) — на Android 10+ только если Sinhron в это время на экране (фоновому приложению буфер не читается, а стираем, только убедившись, что там наши слова); на iPhone копия может уйти на Mac/iPad (Universal Clipboard) — пометка «только это устройство» требует нативного кода, не сделано (storage-devices:8). Поля ввода 24 слов — без автозамены, подсказок и обучения клавиатуры (запись 229). ADR-059: пока человек не сохранил слова («Позже» при регистрации), они лежат на первом телефоне рядом с ключом устройства (A12) — тот же Keychain / Keystore, «только это устройство»; кто достал A12, и так может всё, что дают слова (ADR-021), — лишнее только то, что слова можно прочитать глазами; после первого сохранения запись удаляется.

- Индекс поиска (FTS5, v10) лежит в той же базе SQLCipher и зашифрован тем же ключом; удалённые и исчезнувшие сообщения удаляются из индекса триггерами вместе со строкой. С v12 (ревью 2026-10-13) у индекса включён `secure-delete` (иначе FTS5 хранил триграммы удалённого текста в своих сегментах до слияния), а у базы — `PRAGMA secure_delete = ON` (освобождённые страницы затираются нулями).

**Остаточный risk.** State-level forensic с extracting RAM from running phone — out of scope (T10).

### T7 — Malicious peer in same chat

**Защита.**
- MLS guarantees: только members of the group decrypt. Removed member loses access immediately (key rotation на каждый Add/Remove).
- Forward secrecy: even if peer leaks their MLS state to attacker, past messages remain confidential after next Commit.
- Post-compromise security: even if MLS state compromised, after next Update Commit attacker is out.

**Не можем.**
- Member может screenshot / out-of-band leak content. Это **информационный** контроль, не криптографический. Standard messenger limitation.
- Safety number verification («О чате» → «Проверить собеседника»; в приложении — «код проверки») даёт users out-of-band способ проверить identity peer'а; в группе — для каждого участника отдельно («О чате» → участник).
- Снимок и запись экрана (ADR-030 + дополнение): в чате с исчезающими сообщениями собеседники узнают о снимке или о записи экрана (один раз на запись) — но только если снимок сделан этим приложением на этом телефоне без изменений; изменённый клиент или фото экрана другим устройством не сообщат ничего. Это вежливость, не защита (T7, «Не можем»).
- Правка и «удалить у всех» принимаются только в течение 24 ч после отправки (+ сутки на доставку для входящих, `sinhron_storage::EDIT_WINDOW_SECS`/`LATE_ACTION_GRACE_SECS`): участник с изменённым клиентом не перепишет старую историю на чужих экранах. Время сообщения — локальное время получателя, так что граница проверяется по его часам.
- Имя участника (`profile`, tag 13) — заявление самого участника: можно назваться чужим именем. Защита: имя очищается от управляющих, bidi и zero-width символов (нельзя развернуть текст или спрятать различие), длина ≤ 64; отличить людей с одинаковым именем — по коду безопасности. Фото в `profile` — тоже заявление (можно поставить чужое фото); метаданные: отправитель перекодирует снимок (`photo::prepare` — без EXIF/GPS, ≤32 КБ), получатель перекодирует ещё раз перед сохранением (вредоносный JPEG от собеседника не доходит до UI-декодера как есть, мусор просто удаляет фото). Фото не уходит в запросы на переписку и заблокированным, сервер видит только шифротекст. «О себе» (ADR-052, поле 3 `profile`) — так же: очищается от невидимых символов на отправке и на приёме, одна строка ≤ 200 символов (длиннее — обрезается), не уходит в запросы на переписку и заблокированным; при блоке собеседнику уходит профиль без него (стирается у него). Видят все участники общих чатов, включая группы. Контакты (ADR-052) хранятся только на устройстве, в зашифрованной базе — сервер списка знакомств не видит.
- Форматирование (ADR-070) — данные собеседника: Rust у получателя оставляет только диапазоны внутри текста на границах символов, известных видов, не больше 1000; ссылка-слова — только `https://` `http://` `mailto:` `tel:` без пробелов и управляющих символов (`javascript:`, `file:`, `intent:` и схемы приложений отбрасываются — слова остаются). Ссылка, у которой слова не совпадают с адресом (фишинг «Сайт банка» → чужой адрес), открывается только через лист с настоящим адресом и предупреждением; любые ссылки — только после подтверждения. Язык блока кода — только `[A-Za-z0-9+#._-]` (не попадает в разметку). Испорченный JSON или диапазон — нет форматирования, текст остаётся.
- Картинки и имена файлов от собеседника (запись 232, `security-review-2026-11` app-surface:4, :6, :8, critic:8): png/webp-стикер со стороной больше 2048 и фото профиля больше 1024 отвергаются по заголовку, до декода (картинка-бомба в 31 КБ = ~1 ГБ памяти); имя файла теряет символы направления текста, невидимые и управляющие (`photo‮gpj.exe` не выглядит как `.jpg`); zip стикеров распаковывается с пределом 1 МБ на файл, размер из заголовка не доверяется. Самообновление (ADR-058) обрывает загрузку, как только пришло больше объявленного; APK больше 200 МБ не принимается.
- Запрос на переписку (хранилище v11): пока чат, начатый другим, не принят, ему не уходят отчёты о прочтении, «печатает» и моё имя, а звонки из него не звонят — незнакомец не узнаёт, что я прочитал(а) и кто я. Отчёты о доставке уходят (как в Signal) — то, что сообщение дошло до устройства, он узнаёт.
- Запросы и блокировка — ничего лишнего наружу (ревью 2026-10-13): в запрос на переписку и в личный чат с заблокированным не уходят отчёты о прочтении, «печатает», реакции, закрепления, моё имя и уведомление о снимке; системные строки (таймер, снимок собеседника) больше не «принимают» запрос. Звонок, который отсеян (выключены входящие, заблокирован, запрос, чат не на этом устройстве), **игнорируется, а не отклоняется**: отказ сообщил бы звонящему, что устройство в сети и отсеивает его, и (звонки на сервере — по человеку) оборвал бы звонок на других моих устройствах.
- Блокировка (ADR-071, 2026-10-19): сообщения и действия заблокированного отбрасываются на устройстве, **и** отзывается ключ доступа, который я дал именно ему: сервер молча выбрасывает его доставки без входа (ответ — как при успехе, push нет), его запасные пути (WS, обычный `Submit`) доходят до открытого приложения без push, его звонок проглатывается. Сервер видит только «хэш X отозван» — чей это хэш, он не знает (ключ передан внутри MLS). Исключение — звонки: сервер знает звонящего, поэтому в момент звонка заблокированного он видит своё решение «не звонить» (подробнее — §5, п. 22). Заблокированный участник группы остаётся в группе и читает ваши сообщения — это MLS-членство, а не блокировка. «Звонит…» у звонящего (status 213, `CallRing.delivered`) значит «вызов дошёл до открытого соединения собеседника» — так звонящий узнаёт, что телефон в сети (как в WhatsApp); заблокированному и тому, чей телефон выключен или не проснулся, показывается одинаково «Вызов…» — блок по-прежнему не отличить от выключенного телефона.
- Незнакомые (ADR-071): у человека без моего ключа (первое сообщение, непринятый запрос) путь только «запросом»: доходит в открытое приложение, не больше 60 в минуту от одного человека одному. Ключ уходит собеседнику только после принятия запроса (или в чате, начатом мной). Дополнено (status 177): о запросе сервер шлёт push **без содержимого** (раз в 10 минут от одного одному, 10 в час одному) — iPhone получает фоновый push и показывает тихое «Новый запрос на переписку» сам, Android — `{"t":"req"}`; **заблокированному телефон ничего не показывает** (решает по своему списку и отправителю из запечатанного превью). Сервер шлёт этот push одинаково и незнакомому, и заблокированному — блокировки он не узнаёт. Звонки приложений старше 0.7.0 (без ключей) на время перехода будят телефон (`SINHRON_LEGACY_CALL_PUSH`); Android не звонит заблокированному — ключ звонящего лежит внутри зашифрованного ключом телефона push (Google / ntfy видят шифротекст одного размера, 256 байт).
- Ссылки-приглашения (ADR-043): `https://<сервер>/join#<данные>.<подпись>` — сервер, ключ и имя пригласившего подписаны его ключом (Ed25519, домен `sinhron-invite-v1:`; на дополнительном устройстве — ключом устройства + сертификат устройства). Изменённая ссылка (другой сервер, ключ, имя) или ссылка, перенесённая на другой домен, — отказ («изменена или подделана»). Подпись НЕ доказывает, что имя правдиво: любой может сделать подписанную ссылку на свой ключ с любым именем — поэтому перед добавлением приложение показывает сервер и начало ключа, а сверка — по коду безопасности. Всё после `#` браузер не отправляет — сервер и его журналы не видят, кто кого пригласил. Страница `/join` выполняет ровно один встроенный скрипт (CSP с хешем, сверяется тестом). Короткая ссылка `https://<сервер>/i/<id>#<ключ>` (2026-11-03): длинная лежит на сервере зашифрованной (AES-128-GCM, ключ только во фрагменте, id — связанные данные), год; сервер знает, что приглашение создано и когда, и IP/время открывшего — но не кто приглашает и не имя; подменить блоб он не может (не расшифруется, а внутри — та же подписанная ссылка). Сервер внутри ссылки (запись 232, `security-review-2026-11` app-surface:1, :3) — только имя домена с необязательным `:порт`: ссылка с `http://`, путём, `user@` или голым IP — «повреждена»; новичок по приглашению попадает только на `wss://`. Ответ сервера на короткую ссылку — не больше 16 КБ. Открытие короткой ссылки всё ещё обращается к серверу из ссылки до нажатия (IP открывшего) — открыто.
- Ссылки-приглашения (ADR-043): `https://<сервер>/join#<данные>.<подпись>` — сервер, ключ и имя пригласившего подписаны его ключом (Ed25519, домен `sinhron-invite-v1:`; на дополнительном устройстве — ключом устройства + сертификат устройства). Сервер из ссылки запрашивается только после нажатия (`app-surface:3`, 2026-11-04): с аккаунтом на другом сервере — сразу строка «Этот человек на сервере …», без сети; без аккаунта — окно с адресом сервера и кнопкой «Открыть ссылку»; сервер с `@` и прочими лишними знаками не принимается. Экран приглашения без аккаунта проверяет сервер (`/_healthz`) тоже только по нажатию. _С 2026-11-12 (аудит 2026-11b, WEB-4):_ после истечения короткой ссылки её id остаётся занятым навсегда (содержимое стирается) — старую ссылку нельзя подменить; на сервере не больше 100 000 живых коротких ссылок, сверх — 503, приложение даёт длинную ссылку. Остаток: прохожий с большой сетью адресов может занять весь потолок и на год выключить короткие ссылки (длинные работают).
- Ссылки-приглашения (ADR-043): `https://<сервер>/join#<данные>.<подпись>` — сервер, ключ и имя пригласившего подписаны его ключом (Ed25519, домен `sinhron-invite-v1:`; на дополнительном устройстве — ключом устройства + сертификат устройства). Изменённая ссылка (другой сервер, ключ, имя) или ссылка, перенесённая на другой домен, — отказ («изменена или подделана»). Подпись НЕ доказывает, что имя правдиво: любой может сделать подписанную ссылку на свой ключ с любым именем — поэтому перед добавлением приложение показывает сервер и начало ключа, а сверка — по коду безопасности. Карточка контакта в чате («Поделиться контактом», `sinhron-contact:<ключ>@<хост>?n=<имя>` обычным сообщением) не подписана вовсе: имя — что набрал отправитель. С 2026-11-04 (`app-surface:9`) карточка показывает «Адрес» (начало ключа), человека, которого я уже знаю по этому ключу, — под моим именем для него (и чат открывается под ним), а незнакомого — с пометкой «Имя из карточки, не проверено». Предел: если по карточке незнакомого начат новый чат, имя с карточки остаётся названием чата (профиль собеседника заменяет только «Чат xxxx»). Всё после `#` браузер не отправляет — сервер и его журналы не видят, кто кого пригласил. Страница `/join` выполняет ровно один встроенный скрипт (CSP с хешем, сверяется тестом). Короткая ссылка `https://<сервер>/i/<id>#<ключ>` (2026-11-03): длинная лежит на сервере зашифрованной (AES-128-GCM, ключ только во фрагменте, id — связанные данные), год; сервер знает, что приглашение создано и когда, и IP/время открывшего — но не кто приглашает и не имя; подменить блоб он не может (не расшифруется, а внутри — та же подписанная ссылка). Сервер из ссылки запрашивается только после нажатия (`app-surface:3`, 2026-11-04): с аккаунтом на другом сервере — сразу строка «Этот человек на сервере …», без сети; без аккаунта — окно с адресом сервера и кнопкой «Открыть ссылку»; сервер с `@` и прочими лишними знаками не принимается. Экран приглашения без аккаунта проверяет сервер (`/_healthz`) тоже только по нажатию. _С 2026-11-12 (аудит 2026-11b, WEB-4):_ после истечения короткой ссылки её id остаётся занятым навсегда (содержимое стирается) — старую ссылку нельзя подменить; на сервере не больше 100 000 живых коротких ссылок, сверх — 503, приложение даёт длинную ссылку. Остаток: прохожий с большой сетью адресов может занять весь потолок и на год выключить короткие ссылки (длинные работают).
- Самообновление Android (ADR-058): манифест `/download/android.json` и APK берутся с сервера человека по https; перед установкой — SHA-256 из манифеста, пакет `com.sinhron.sinhron`, код версии выше установленного и **сертификат подписи = наш** (зашит в приложение, `kApkCertSha256`). Кто взломал сервер или подменил ответ, может только показать карточку «Доступно обновление» и отдать файл — установить чужое приложение не сможет (и Android сам не обновит приложение файлом с другой подписью). Установщик получает файл через свой `FileProvider` (только `cacheDir/updates/`), человек всегда нажимает «Установить» сам. Установленные из магазина и отладочные сборки не обновляются этим путём.
- UnifiedPush (ADR-040, Android): сервер POST'ит только на `https`-адреса хостов из `SINHRON_UNIFIEDPUSH_HOSTS` (свой ntfy), без редиректов — подставленный адрес не заставит сервер ходить во внутреннюю сеть (SSRF). Тело — бейдж или id звонка, **зашифровано ключом телефона** (Web Push RFC 8291, aes128gcm; `server/src/webpush.rs`, 2026-10-16): ntfy видит только шифртекст, размер и время. Ключи телефона (p256dh, auth) приходят вместе с адресом и подписаны ключом устройства; адрес без ключей сервер не примет. Телефон отбрасывает нешифрованные push — тот, кто узнал адрес ntfy, не подделает «входящий звонок». Свой ntfy (ADR-087, 2026-11-04): подписываться можно без входа (имя темы — случайное, знают только телефон и сервер), публиковать — только сервер своим токеном (`SINHRON_NTFY_TOKEN`; токен уходит только на первый хост списка) — чужие больше не пользуются им как бесплатной пересылкой. Ключ устройства на Android — в Keystore; бэкап приложения выключен. `GET /v1/push/info` (без входа) называет эти хосты — они и так публичны (DNS-имена оператора); телефон показывает их человеку, чтобы ntfy смотрел на свой сервер, а не на ntfy.sh.
- Жалобы (ADR-037): жалоба уходит оператору сервера (с ADR-077 — и администраторам в чат «Сервер», с IP обеих сторон на 30 дней), подписанная ключом жалующегося; текст сообщения — только если жалующийся сам решил его отправить (тогда оператор читает его открытым текстом). Ложная жалоба возможна — решает человек-оператор; от одного человека не больше 50 в сутки. Удаление аккаунта подписывается только ключом личности (не ключом привязанного устройства) — украденный привязанный телефон без 24 слов аккаунт не удалит. _Аудит 2026-11b (2026-11-12):_ текст жалобы в чате «Сервер» — чужой ввод: в уведомлении он только в последней строке «Сообщение: «…»», одной строкой; всё, что выше, пишет сервер. Ключ для `reports.sh ban` брать из строки «Ключ нарушителя» (она выше цитаты). Бан блокирует ключ личности (ADR-098); новый ключ = новый аккаунт без прежних контактов — это не закрывается.
- Права админа группы (ADR-035) соблюдают **клиенты**, не криптография: админ записан в контексте группы MLS (ADR-088, запись 242): его ставит создатель, а когда админ уходит, роль переходит к самому раннему оставшемуся человеку по правилу, которое считает каждый телефон. Commit, ставящий другого админа, телефоны не применяют. Только переименование от админа принимают остальные. Участник с изменённым клиентом может закоммитить чьё-то удаление (MLS это позволяет любому участнику; тем же путём честные приложения убирают вышедшего) — с записи 231 все обновлённые увидят строку «X удалил(а): Y» с настоящим автором Commit'а. **Добавить нового человека** может только тот, кто управляет (админ, а без админа — любой): Commit не-админа с новым человеком обновлённые телефоны не применяют (mls-identity:3); любое добавление нового человека показывается строкой «X добавил(а): Y». Цена отказа: телефон, не применивший Commit, отстаёт от чата (новые сообщения не читаются) — лучше, чем впустить чужого. Старые приложения такой Commit по-прежнему применяют молча. Новые устройства уже бывших в чате людей добавляет любой без строки (ADR-074). С записи 242 (mls-identity:8) новичок на освободившемся листе 0 не становится админом, а смена телефона админа роль не забирает. Остаётся: участник с изменённым приложением может удалить админа (тот же путь, что честный выход), и роль перейдёт к самому раннему оставшемуся — то есть сделать админом себя (аудит 2026-11b CM-08; прежняя фраза «изменённое приложение не сделает себя админом» была неверна). _Не закрыто (2026-11-12): правило «админа убирает только Commit после его „выхожу“» сделано и откатано после проверки — решение владельца._ _Закрыто 2026-11-12 (ADR-102): подмена человека на своём листе (CM-07) и показ сообщения без подтверждённого отправителя (CM-09)._ _Потерянный ответ сервера (CM-03, ADR-101, 2026-11-12): раньше устройство молча и навсегда выпадало из чата; теперь Commit ждёт своего эха или повторной отправки. Сервер по-прежнему может не доставить Commit (отказ в обслуживании) — это видно как «не отправляется», а не тихо._ Выход на сервере (`POST /v1/groups/{id}/leave`) подписан ключом личности (домен `sinhron-group-leave-v1:`): убрать из рассылки можно только себя.
- Права админа группы (ADR-035) соблюдают **клиенты**, не криптография: админ — создатель (лист 0 MLS), только его переименование и строку «удалил» принимают остальные; но участник с изменённым клиентом может закоммитить чьё-то удаление (MLS это позволяет любому участнику). Все увидят, что человек исчез из списка участников, только без строки «X удалил Y». Выход на сервере (`POST /v1/groups/{id}/leave`) подписан ключом личности (домен `sinhron-group-leave-v1:`).
- Состав чата на сервере (ADR-083, 2026-11-04, `docs/security-review-2026-11.md` server-http:1, critic:5, calls:4): `POST /v1/groups` подписан устройством (домен `sinhron-group-announce-v1:`); вписать устройства в существующий чат может только человек, который уже в нём (или чьё устройство там отключили — только своё новое); новый чат — подписавший в своём списке. Удалившее приложение подписывает `POST /v1/groups/{id}/remove` (`sinhron-group-remove-v1:`): сервер вычёркивает все устройства удалённых (и их отключённые устройства — карточку чата они больше не получат) и выгоняет их из комнаты звонка; отключённое устройство тоже выгоняется из звонков; токен LiveKit живёт 10 минут. Пределы: (неподписанный запрос — 401 с 2026-11-04, переключатель `SINHRON_LEGACY_GROUP_ANNOUNCE` убран, ADR-087); любой участник может вычеркнуть другого из рассылки (сервер Commit не читает — но удалить в MLS он может и так); вписать в новый чат чужое устройство (мусорный чат, приглашения) может любой зарегистрированный. **Честные пределы после аудита 2026-11b (открыто):** GRP-1 — участник одним `/remove` вычёркивает весь состав, чат на сервере мёртв (правка откатана). GRP-2 / PREV-1 — состав чата на сервере ≠ состав MLS: участник может вписать устройство своего второго аккаунта без Add в MLS; оно переживает удаление вписавшего и для сервера остаётся участником (получает Commit'ы и метаданные, карточки чата, токен звонка, может менять состав и таймер). Переписку не читает (нет ключей MLS). _С 2026-11-12:_ лимит 600/ч на устройство и 1000 чатов на создателя, `get_card` отдаёт не больше 32 карточек (GRP-3); `/leave` теперь тоже закрывает вход по карточке для отключённых телефонов ушедшего и выводит его из звонка.
- Без переходных режимов (ADR-087, 2026-11-04, `docs/security-review-2026-11.md` server-http:11, sealed-push:4, server-http:5, server-http:7, server-http:14, critic:6, calls:10, server-ws:9, sealed-push:6): заблокированный с моим старым общим ключом больше не доставляет; его запасные пути (WS, `Submit`) с отозванным ключом доходят без push (раньше переключатель давал push); у своих — обычный push по любому пути: `Submit`/`SealedSubmit` несут ключи, которые собеседники дали отправителю (без ключа — push «запрос»; сервер на этих путях узнаёт, что отправитель держит ключ собеседника). Взять мои KeyPackage может только зарегистрированное устройство с подписью (`sinhron-kp-consume-v1:`), не аноним; _с 2026-11-12 (DEV-4) один аккаунт — не больше 10 в час у одного человека; несколько аккаунтов по-прежнему могут осушить запас (не закрыто)._ «Был в сети» в `GET /v1/devices` — только день, не секунда. Чужой аккаунт, узнавший мой push-токен, больше не снимает его с моего телефона (может только добавить себе — тогда шлёт на мой телефон своё «Новое сообщение»; не закрыто). Звонящий без моего ключа не узнаёт, что приглашение дошло до открытого приложения (видит то же, что заблокированный). Ответы сервера на кадр приходят только в соединение, которое его послало. Полученный запечатанный конверт сервер хранит 30 дней, не год. Сервер входит в базу своей ролью без прав суперпользователя (новые установки; существующая — после переключения, `deploy-guide.md` §9.1).

**Код.** `openmls 0.9.2` group operations (industry-standard MLS RFC 9420 implementation).

### T8 — Compromised public CA

**Защита.** TLS pinning (B3). После операторского deploy'а с pinned CA в Info.plist / bundled bytes, только этот CA может подписать legitimate cert. Compromised public CA's fraudulent cert не валидируется.

**Код.** `sinhron_net::TlsPinning::from_pem` — constrained `rustls::ClientConfig` с только operator CA в RootCertStore.

### T9 — Operator infrastructure compromise (root on VM)

**Не защищаем.** Если у attacker root на серверном VM, он может:
- Modify server binary → inject fake Auth handshake, бросить fake Push'и
- Read .p8 → MITM APNs; read `/etc/sinhron/fcm/service-account.json` (ADR-057) → слать FCM-push от имени проекта (телефоны отбросят незапечатанные их ключами — но ключи телефонов лежат в той же БД, `apns_tokens.call_hint_key`). Позвонить «от имени» контакта — нет (ADR-090, 2026-11-04): приглашение подписывает сам звонящий, телефон называет звонок только по верной подписи участника чата; без неё — «Sinhron» на iPhone до подключения приложения, которое такой звонок снимает
- Inject server logs / forge metrics
- DOS

**Mitigation на operator side.**
- ACLs (`POSTGRES_PASSWORD` only readable by sinhron-server uid)
- Docker secrets (not env vars) for production
- VM hardening (ufw, fail2ban, no public SSH)
- Backup encryption (см. T1.1 — local backup must also be encrypted). С записи 233: `backup.sh` без пароля ничего не сохраняет; `restore.sh` берёт только `.gpg`, открытые паролем копий (`DECRYPTION_OKAY`), — подложенный в копию вне сервера открытый дамп или файл `gpg --store` не загрузится. _С 2026-11-12 (аудит 2026-11b, ветка deploy):_ сбой `pg_dump` (Postgres не отвечает, обрыв) больше не оставляет пустой файл под именем хорошей копии дня — раньше `restore.sh` взял бы его и очистил базу. Остаётся: `restore.sh` проигрывает дамп от суперпользователя базы и не в одной транзакции (обрыв посреди восстановления оставляет полбазы) — сырые находки backup-02 / backup-03, не проверены и не чинились; целостность копии не проверяется.
- Установщик и сборка (аудит 2026-11b, 2026-11-12): сбой генерации секретов не обнуляет `server/.env`; `--commit` не пропускается молча при локальных правках; `--config` в чужой папке не меняет её права. Еженедельный `cargo audit` снова зелёный: RUSTSEC-2026-0459 (SQLite) принят как остаточный риск до 2027-02-01 — в сервере не собирается, в телефоне только свои локальные базы SQLCipher (ADR-109). CI: токен workflow только на чтение; `cargo test --locked` и `flutter pub get --enforce-lockfile` — расхождение с lock-файлами теперь ошибка CI. Пароль ключа подписи Android больше не виден в списке процессов при сборке (deploy-deps:17 закрыто). Остаётся (сырое, D-04/D-14/D-16/D-17/D-05): папка кода принадлежит обычному пользователю, а cron от root запускает из неё скрипт; шаг SSH объявляет «только по ключу» без проверки; обновление выполняет старый установщик; образы Docker по тегам; `push.<домен уровнем выше>` при автопоиске имени ntfy. Действия GitHub закреплены тегами, не SHA (deploy-deps:13 / ci:6); `--locked` нет в Dockerfile сервера, в cargokit и в скриптах сборки для телефонов; graphify ставится «самой свежей» версией (ci:1). Пароль ключа Android лежит рядом с ключом открытым текстом, копия ключа вне Мака не подтверждена (build:2). Не закрыто, меняет работающий сервер (см. tech-debt): общий запас запросов ntfy на все телефоны Android (D-34, средняя); журнал ошибок Caddy хранит IP и путь (D-35); пароль суперпользователя Postgres по умолчанию `dev_only` при ручной установке без установщика (D-25); push на любой путь своего ntfy (D-33).
- Контейнеры (запись 233): у всех `cap_drop: NET_RAW`, у всех кроме coturn (его образ запускается с file capability) — `no-new-privileges`; Caddy режет тело запроса до 1 МБ на именах LiveKit и ntfy (LiveKit до проверки токена пишет большое multipart-тело на диск). Журналы сервера — только начало id групп и `user_pk` (12 знаков). Ещё открыто: приложение ходит в Postgres суперпользователем, Postgres в общей сети с Caddy/LiveKit/ntfy, ntfy принимает публикации от всех (решение владельца — запись 233).
- Monitoring + alerting (T2.4 / metrics)

**Client защита (что мы делаем).**
- Обновление сервера — только до коммита, который назвал оператор (`install.sh --commit <id>`, ADR-090): кто может писать в репозиторий, не получает root на сервере при следующем `--yes` (и в ночном cron копий из того же дерева). Без `--commit` код не обновляется.
- MLS state — client-side encrypted backup (T1.2) на server. Если operator wipes БД — recovery via phrase + state_backups blob.
- Action proofs validate sender's signature — admin не может подменить sender_user_pk без compromising user's Ed25519 private key (которое только в DerivedIdentity holder).

**Соседние сайты на том же сервере (status 203).** Caddy обслуживает домены других проектов оператора по файлам `/etc/sinhron/caddy-sites/*.caddy` и состоит в общей сети `edge`. Писать туда может только root — это та же граница доверия, что T9. Чем это рискует Sinhron: (1) ошибочный файл не применится при `reload`, но не даст Caddy стартовать после перезапуска → API и звонки через 443 недоступны (доступность, не конфиденциальность; runbook требует `caddy validate`); (2) соседний блок с именем Sinhron ломает конфигурацию целиком (тоже только доступность); (3) скомпрометированный соседний контейнер в `edge` видит только Caddy (его порты 80/8443/443 — то же, что из интернета; PROXY-заголовок принимается только с 127.0.0.1), а не `sinhron-server`, Postgres, LiveKit — они в сети `default`. **Поправка (запись 221, проверка безопасности 2026-11-02):** соседний `.caddy`-файл исполняется тем же Caddy и видит его `/data` — блок с `root * /data` + `file_server` отдаст TLS-ключи и ключ ACME-аккаунта Sinhron, а блок с путём на имени Sinhron может перехватить часть API. Поэтому писать в `/etc/sinhron/caddy-sites` можно только тому, кому доверяешь как root; изоляция соседей — P1 в `docs/security-review-2026-11-02.md`. `(security_headers)` соседи не наследуют.

### T10 — State-level adversary

**Out of scope для v1.** Если adversary:
- Может subpoena operator → operator должен сам обеспечить metadata-minimization (мы рекомендуем self-hosted)
- Может exploit broker (zero-days) → надо иметь contained blast radius (Rust, sandboxing, immutable infra)
- Может exfiltrate phrase from user (rubber-hose) → not a crypto problem

Sinhron не претендует на anti-state-level threats. Использовать для personal/family/team privacy, не для journalism in authoritarian regimes.

**Сервер владельца в России (с 2026-10-16).** Решение владельца: почти все собеседники — в России (родители, друзья), сервер `chat.777400777.xyz` переехал с DigitalOcean (Франкфурт) к российскому провайдеру (2 выделенных ядра, Ubuntu 24.04). Что это меняет:
- **Содержимое — без изменений:** сообщения, медиа и звонки зашифрованы на устройствах (MLS, SFrame); ключей на сервере нет — ни провайдер, ни госорганы по запросу к нему прочитать их не могут.
- **Метаданные — доступнее:** российский хостинг обязан ставить СОРМ; кто с каким IP и когда соединяется с сервером, объёмы и время звонков (TURN / LiveKit видят IP участников) — доступны без запроса к владельцу. Скрывает IP только прокси / Tor в приложении (ADR-028); звонки идут без прокси.
- **Блокировка:** незарегистрированный мессенджер может быть заблокирован РКН; тогда — сервер за границей и резервный путь (ADR-042) или прокси.
- **Компрометация оператора (T3/T9):** изъятие или копия диска даёт то же, что и раньше (шифротекст, социальный граф, время) — модель не меняется, меняется вероятность.
- **Провайдер:** если хостинг исчезнет (санкции, давление), восстановление — из копии вне сервера (`backup.sh`, держать копию у владельца); переезд — тот же адрес, приложения переподключаются сами.

### T11 — Compromised LiveKit SFU

**Контекст.** LiveKit forwards encrypted SRTP packets между call participants. Не "trusted middleware" — это просто relay. **Mitigation by design:** E2EE поверх через SFrame (RFC 9605) — keys выводятся ТОЛЬКО на endpoints из MLS exporter, никогда не отправляются на сервер.

**Защита.**
- SFrame keys выводятся локально: client → `mls_group_exporter` → `sframe_derive_key_pair` → `BaseKeyProvider.setRawKey`. LiveKit SDK получает уже-encrypted frames; никогда не видит plaintext.
- JWT issued by sinhron_server (HS256) — LiveKit verifies signature, но не имеет SFrame key material.
- Verified в `examples/calls_e2e.rs`: Alice и Bob выводят bit-identical keys из MLS group, передача через LiveKit невозможна для decrypt без membership.

**Остаточный leak.**
- LiveKit видит: participant identity (через JWT claims `sub` + `metadata=group_id_hex`), timing patterns, packet sizes, IP addresses.
- LiveKit видит SFrame KID layout (S=6 + E=4 bits) → может корреллировать sender ↔ packet stream.

**Что НЕ можем.** Если LiveKit binary заменён на malicious — он не получает plaintext, но может injection ciphertext-level — SFrame AEAD reject'нет это integrity-wise (AES-GCM tag fail).

**Сервер не может выключить шифрование (2026-11-04, `docs/security-review-2026-11.md` calls:1–3, запись 226).** В livekit_client 2.7.0 шифратор вешается на дорожку, только если ответ сервера (`TrackInfo.encryption`) говорит «GCM» и кодек не AV1 — это слово сервера, не наше. Раньше приложение это не проверяло: изменённый SFU (или чужой `livekit_url` в ответе `/v1/call/token`) мог ответить «без шифрования», и голос, камера и экран шли бы открытыми. Теперь (`livekit_engine.dart`): (1) каждая моя дорожка (`LocalTrackPublishedEvent`), каждая чужая (`TrackPublishedEvent`, `TrackSubscribedEvent`) проверяется `callTrackEncrypted` — нужен GCM и не AV1; иначе мои микрофон и камера останавливаются, комната закрывается, звонок кончается с причиной `e2ee_downgrade` («Звонок прерван: сервер пытался отключить шифрование»). Старые версии приложения публикуют тоже GCM — честные звонки идут как раньше. (2) «Хвост незашифрованного кадра» (SIF trailer): кадр, кончающийся им, проигрывался без расшифровки. По умолчанию это публичное `LK-ROCKS`, плюс сервер мог прислать свой (`JoinResponse.sif_trailer`) — то есть SFU мог вставить свою картинку или голос от имени участника. Теперь хвост — 32 случайных байта на звонок, никуда не уходит, и серверный не принимается (`CallKeyProvider`). Хвост читает только приёмник — формат на проводе не меняется. (3) Сообщения данных (согласование кодеков, тема `sinhron.codecs`) тоже шифруются: `RoomOptions.encryption` вместо устаревшего `e2eeOptions`.
**Остаётся (нужно решение владельца).** SDK вешает шифратор уже после того, как дорожка согласована: SFU может придержать ответ на публикацию (до 10 с, а с `enabled_publish_codecs` SDK публикует параллельно) и получить первые секунды голоса открытыми — даже если потом ответит «GCM». Закрыть можно только своей правкой livekit_client (`dependency_overrides`: шифратор до `negotiate()`, всегда) — это поддержка своей копии SDK. Целостность сообщений данных тоже не проверить: в 2.7.0 у `DataReceivedEvent` нет типа шифрования. _Частично 2026-11-12 (ADR-110, аудит 2026-11b 05/C-11): сервер, который не отвечает на публикацию, — дорожка без шифратора останавливается через ≤10 с; если это микрофон — звонок завершается, если камера или показ экрана — идёт дальше со звуком._ **Остаточный риск (открыт):** эти ≤10 с звука/видео видны взломанному серверу звонков (tech-debt 2.64); закрывается только своей копией livekit_client (шифратор до negotiate) — не делалось. Нативная сторона (что libwebrtc действительно шлёт открытый RTP на таком отправителе и что `track.stop()` его глушит) — по чтению, на телефоне не проверено.

**Звонки при враждебном сервере звонков — открыто после аудита 2026-11b (2026-11-12).** Заголовок «сервер не может выключить шифрование» читать так: закрыты три пути (calls:1–3). Аудит-2 (черновик области 05, скептиком не перепроверен; тесты на Dart-часть есть, выход «в провод» не снимался) заявил ещё четыре, ждут перепроверки: сервер не отвечает на публикацию дорожки → микрофон и камера идут открытыми весь звонок (05/CALL-darte2ee-1; _в ветке звонков — ADR-110: дорожка останавливается, звонок завершается через ≤10 с, окно ≤10 с остаётся_); сервер просит «вторую копию» видео через dynacast → она идёт без шифратора, хотя резервный кодек выключен (05/CALL-darte2ee-2; _ADR-110: `dynacast: false`_); дорожка «ничьего» участника проигрывается без шифратора (05/CALL-darte2ee-3); сервер «отвечает» на входящий звонок за человека — телефон сам входит в комнату с включённым микрофоном (05/CALL-dartcontrol-1). Ключи SFrame при этом не утекают (I11 не меняется) — утекает открытая дорожка мимо шифратора.

**Дорожки мимо шифратора (ADR-041, 2026-10-16).** livekit_client 2.7.0 вешает SFrame-шифратор только на основной sender дорожки и пропускает AV1. Поэтому: (1) резервный кодек (backup codec — вторая копия видео по запросу SFU) **выключен** в `callVideoPublishOptions`, иначе SFU мог бы запросить незашифрованную копию; (2) `livekit.yaml` `room.enabled_codecs` — только `opus`, `red`, `vp8`, `h264`, `rtx`: AV1 и прочие кодеки сервер не примет. Злонамеренный SFU (T11) сам по себе включить резервный кодек не может — его отправку решает клиент. Тест: `call_quality_test.dart` (backup codec выкл.). _Поправка 2026-11-12 (ADR-110, аудит 2026-11b 05/C-12; правка в ветке звонков, на момент записи в работе): «резервный кодек выключен» само по себе не защищало — livekit_client 2.7.0 не читает `BackupVideoCodec.enabled` на пути, который запускает сервер. Теперь защита — `dynacast: false` + список разрешённых кодеков моей дорожки (VP8/H.264/H.265)._

**Ранний вход звонящего (ADR-063, 2026-10-18).** Звонящий входит в комнату LiveKit, пока у собеседника звонит, с опубликованным, но выключенным до публикации микрофоном (`muted` в `AddTrackRequest`, `MediaStreamTrack.enabled = false`): кадров голоса нет до «ответили»; «Выкл. звук», нажатый за это время, запоминается и не открывается. LiveKit видит участника в комнате раньше (с начала вызова, а не с ответа) — сервер Sinhron о звонке знал и раньше. Отвечающий до ответа в комнату не входит (иначе звонящий видел бы, что его телефон в сети и звонит). Токен LiveKit берётся заранее (он на группу участника, срок час).
**Показ экрана (ADR-061, 2026-10-18).** Экран — ещё одна видеодорожка того же участника; `E2EEManager` вешает шифратор на каждую публикацию, ключ тот же, кодек — H.264 / VP8 из настроек комнаты, резервный кодек выкл. — SFU видит шифр, как у камеры. Остаточные риски — на телефоне, не на сервере: (1) на iPhone в показ попадает весь экран, включая баннеры уведомлений других приложений и вводимый текст — человек сам решает, что показывать, плашка «Вы показываете экран» видна всё время; (2) кадры с экрана идут от расширения к приложению по Unix-сокету в контейнере App Group `group.com.sinhron.sinhron` — внутри песочницы наших двух целей, без шифрования (другие приложения туда не достают); (3) Android: системная остановка MediaProjection не видна приложению (tech-debt 2.49) — дорожка застывает, но новых кадров не отдаёт.

**Код.** `client_flutter/lib/features/calls/livekit_engine.dart::LiveKitCallEngine.connect` (`CallKeyProvider`, `callTrackEncrypted`, `callRoomOptions`); `client_flutter/rust/sinhron_call/src/sframe.rs` (key derivation).

### T12 — SFrame key compromise

**Контекст.** SFrame key = AES-128/256 GCM key + 12-byte salt, derived per (epoch, sender_index). Если attacker получает один — он может decrypt media для того окна.

**Защита.**
- Key material живёт только в RAM (Flutter Dart + Rust). Никогда не персистится, никогда не логируется.
- Per-epoch rotation: каждый MLS Commit advances epoch → новые keys выводятся → старые становятся бесполезными. CC5 rotation: 1s epoch-poll Timer в `LiveKitCallEngine` + LiveKit's built-in 16-slot keyring handles overlap window.
- Identity seed используется для derive — не сама phrase. Phrase wipe'нута через Risk #6.

**Остаточный risk.**
- Compromise device RAM (jailbreak + lldb attach mid-call) → key extractable. T5/T6 mitigations apply.
- Compromise одной (epoch, sender) пары → decrypt только этих frames, не past/future epochs (forward secrecy from MLS).
- FFI boundary: keys пересекают Rust↔Dart через `SframeKeyMaterialHex {key_hex, salt_hex}`. Hex encoding/decoding в RAM — short-lived buffers. Не zeroize'ы дополнительно (TODO).

**Код.** `client_flutter/rust/sinhron_call/src/sframe.rs::sframe_key_pair` + FFI surface `sframe_derive_key_pair` в `api/simple.rs`.

### T13 — TURN credential theft

**Контекст.** TURN credentials выдаются server-side (`GET /v1/call/turn`) — username `<expiry>:<метка>` (с 2026-10-13 без identity — логи coturn не раскрывают, кто звонит; с записи 234 метка — HMAC от личности и дня на секрете, придуманном при запуске сервера: одна на человека на сутки, чтобы `user-quota=24` в coturn считал по человеку — со случайной меткой один бесплатный аккаунт занимал все места ретранслятора), credential = base64(HMAC-SHA1(`TURN_SHARED_SECRET`, username)). Action-proof signed по `CALL_TURN_DOMAIN`. TTL configurable via `TURN_TTL_SECS` (default 24h — coturn перепроверяет креды на каждом refresh allocation, а mid-call re-mint нет; ADR-016).

**Защита.**
- Bounded TTL (24h default, max 24h) — stolen creds expire within a day.
- Action-proof gating: client должен подписать request своей Ed25519 key → не любой может запросить creds.
- Rate-limited на server side (как все endpoints).
- HMAC-SHA1 secret never exposed client-side; only server can mint.

**Что атакёр МОЖЕТ.**
- Hijack stolen creds в TTL окне → использовать TURN relay для собственного traffic (DDoS amplification, NAT traversal piggyback).
- TURN provider видит metadata: who relay'ит, when, какой volume.

**Что атакёр НЕ может.**
- Decrypt SFrame media (E2EE-encrypted поверх).
- Занять больше 24 мест ретранслятора на один аккаунт (запись 234). **Поправка (проверка 2026-11):** «долгой злоупотребы нет» — неверно: регистрация открыта, любой новый аккаунт получает данные TURN, а ретранслятор пускает к любому публичному адресу (не только к LiveKit). Закрыть — только LiveKit как разрешённый адрес (`allowed-peer-ip`), это решение владельца. _Аудит 2026-11b (2026-11-12, LIMIT-1):_ квота TURN на человека до этого не действовала; теперь имя одно на человека на сутки. Остаток: после перезапуска сервера и в полночь UTC человек получает второе имя (ещё 96 мест). TURN к любому публичному адресу для любого зарегистрированного — по-прежнему открыто (LIMIT-5), вред ограничен квотой на человека. `/v1/call/*`: ковш только у аккаунтов (LIMIT-3). Заявлено аудитом, не перепроверено (черновик области 10, 10/DEP-3-*): relay coturn достаёт до UDP-портов самого сервера.

**Mitigation на operator side.**
- Monitor coturn metrics (`/metrics` если scraping) для unusual relay patterns.
- Rotate `TURN_SHARED_SECRET` периодически (требует server restart).
- Firewall: coturn relay range ограничен `min-port`/`max-port` = 49152-49999/udp (turnserver.conf); `no-tcp-relay` — TURN нельзя использовать как generic TCP-прокси (подключение клиента по TCP/TLS 443 это не трогает — ADR-041); `denied-peer-ip` закрывает приватные сети, Postgres слушает только 127.0.0.1.

**Код.** `server/src/handlers/call.rs::mint_turn_creds` + `server/turnserver.conf`.

**Доступ в комнату звонка (с 2026-10-13).** `POST /v1/call/token` выдаёт LiveKit JWT только участнику MLS-группы (`is_group_member`: `group_members → devices → users`), иначе 403. До этого любой владелец Ed25519-ключа, знающий `group_id`, мог войти в SFU-комнату: медиа не расшифровать (SFrame), но видны участники/время и можно мешать звонку. `POST /v1/call/live` (2026-10-18) под той же проверкой отвечает только «есть ли кто-то в звонке» — участнику группы, который и так видит звонок.

## 5. Known limitations (документируем явно)

1. **Sealed sender (§6.5) — что ещё видно серверу.** С ADR-023 чат и содержимое скрыты; с ADR-026 конверт уходит **без аутентификации**, когда у отправителя есть ключ доступа получателя (с ADR-071 — свой у каждого собеседника; без ключа — только этим получателям, по WS), — сервер не знает аккаунта-отправителя; ключ доступа меняется (старый отвергается сразу). IP прячется прокси SOCKS5 / Tor (ADR-028), если он включён; без него IP виден. Остаётся: время запроса; первые сообщения нового чата, пока ключи не разошлись, идут аутентифицированным `SealedSubmit`; таймер чата у запечатанных доставок виден как число; звонки идут без прокси.
2. **Несколько устройств (ADR-025/027).** Ключ личности хранится **только на первом устройстве**. Остальные (привязанные по QR или вводом 24 слов) держат пакет со своим ключом и сертификатом; сервер принимает их подпись, пока устройство не отозвано (`accounts::resolve_signer`) — отзыв запирает его (живые соединения закрываются сразу, вход WS и подписанные запросы отвергаются; лист MLS удаляется). Отзывать и добавлять устройства — только ключом личности (на других устройствах — ввод 24 слов на этот шаг, слова не хранятся). Кто знает 24 слова, владеет аккаунтом — украденный телефон вместе со словами не защитить ничем, кроме нового аккаунта. QR-привязка: пакет запечатан на одноразовый ключ из QR; риск — социальная инженерия. Код — один раз: если его ответ или взятие опередил кто-то другой, старый телефон получает 409 и предупреждает «код уже использован другим устройством» (ADR-091); отпечаток аккаунта на новом телефоне до входа — отдельная тема (`storage-devices:13`). Список устройств человека публичен. Welcome адресуются устройствам и удаляются, как только устройство их получило. Группы хранят ключи 2 прошлых эпох (`MAX_PAST_EPOCHS`) — сообщение, отправленное рядом с Commit, не теряется; цена — прямая секретность наступает на 2 Commit позже. «Избранное» (ADR-055) — обычная MLS-группа из одних моих устройств: сервер хранит шифротекст и видит группу одного человека (членство он видит и в любом чате), содержимого — нет; новое устройство получает из старых заметок только последние 200 (история ADR-025).

После отзыва (ADR-084) у аккаунта новое поколение корня ключей доставки и ключа копии — из свежих случайных байт, моим устройствам — внутри группы «только мои»: отозванное не вычисляет новые ключи доставки и не открывает новые копии; ключ доступа (`access_root`) остаётся вычислимым — оно может писать мне без входа (спам, не чтение). _Исправлено 2026-11-12 (ADR-103): новое поколение теперь действительно доходит до остальных моих устройств. Внешний конверт для своих устройств — ключ поколения 0 (его может вычислить и отключённое устройство); тайну содержимого держит MLS группы своих устройств. Собеседники берут самый новый опубликованный ключ доставки недели; ключ поколения 0 публикуется только для сообщений между своими устройствами._ **Уточнение (аудит 2026-11b, DEV-1 / PROOF-2):** «отзыв запирает» верно для ПРИВЯЗАННОГО устройства. Для первого телефона (на нём ключ личности) отключение закрывает вход по WS, но подписанные HTTP-запросы ключом личности сервер по-прежнему принимает — и не может иначе: этим же ключом хозяин входит по 24 словам. Потерянный первый телефон = потерянный ключ личности (п. 26 «кто вытащил ключ аккаунта — тот и есть аккаунт»); защита — блокировка телефона, а не отключение. _С 2026-11-12:_ сервер принимает только строгие подписи Ed25519 — ключ малого порядка («одна подпись на всё») не регистрируется и не подписывает сертификат (PROOF-3); привязанных устройств не больше 8 одновременно (теперь и при одновременных запросах), не больше 32 привязок за 30 дней, публичный список устройств — не больше 64 записей (DEV-2, DEV-3). Своё взломанное устройство до отключения: часы из будущего больше не закрепляют настройки (DEV-2); «Избранное» из переноса — только группа своих устройств (XFER-6, часть); подделка чужих сообщений через перенос — остаётся. Ответ `/v1/media` ограничен 101 МиБ — враждебный сервер не съест память телефона (XFER-2). **Что отзыв гарантирует после 0.12.0 и что остаётся (аудит 2026-11b):** закрыто — новые ключи доходят до остальных своих устройств (06/DEV-1, ADR-103), телефон не возвращает отключённое устройство в чаты (06/PAIR-1, 06/XFER-7, ADR-104). Остаётся при отключённом устройстве **вместе с враждебным сервером**: копия в облаке (06/BKP-1, п. 24), превью в push (06/PAIR-2, п. 20), звонки (05/CALL-server-1), возврат по карточке (CM-12, п. 26). Заявлено аудитом, скептиком не перепроверено (тест есть): из-за `MAX_PAST_EPOCHS` удалённый участник ещё две эпохи может писать в чат (02/crypto-old-epoch-removed-sender). Кто знает 24 слова, владеет аккаунтом — украденный телефон вместе со словами не защитить ничем, кроме нового аккаунта. 3. **APNs cert** требует Apple Developer аккаунт оператора. Server code (T E3) готов; cert provision — ops.
4. ~~**PushKit VoIP**~~ — сделан 2026-10-16 (ADR-039): VoIP-push несёт только id звонка и «видео/аудио» — Apple видит время звонка и устройство, но не звонящего и не группу. Звонок, отсеянный приложением (блокировка), мелькает на экране до подключения — iOS требует показать каждый VoIP-push. **ADR-056 (2026-10-18):** + `h` — HMAC(ключ телефона, call id ‖ group id), своё на каждый звонок; телефон сразу показывает имя чата, Apple звонки одного чата не связывает. С 2026-11-04 (`storage-devices:9`, владелец: «исправь всё» — отменяет просьбу из записи 109) звонки не пишутся в «Телефон → Недавние» (`includesCallsInRecents = false`) — до этого имя чата, время и длительность каждого звонка попадали туда, в бэкап iCloud и на другие устройства Apple ID; старые записи человек удаляет сам.
5. **Padding sidechannel — частично закрыто 2026-10-13.** MLS app messages паддятся до кратного 512 Б (`sinhron_sync::group::PADDING_SIZE`, RFC 9420 §6.3.1) — сервер видит бакет, а не точную длину. Остаётся: бакеты для длинных сообщений, timing, нет cover traffic; SFrame size patterns в звонках leak duration/silence patterns.
6. **Calls implemented (Phase 3 ✅).** LiveKit v1.11.0 + coturn 4.6.3 + SFrame (RFC 9605). E2EE через MLS exporter → SFrame keys. 1:1 functional; group calls (≥3 leafs) — deferred milestone.

20. **Превью в push (ADR-056).** Подписано ключом устройства отправителя и привязано к ключу доставки получателя; старше суток — не показывается. 18. **Чужой адрес сервера (ADR-032).** Адрес вводят или сканируют (QR `sinhron-server:`); подсунутый адрес или QR приведёт человека на чужой сервер. Приложение проверяет только, что там сервер Sinhron (`/_healthz`), — не чей он. Содержимое защищено MLS и там, но метаданные (кто, когда, с кем) увидит тот сервер. Адрес — только от того, кому доверяете; сервер показан в «Настройки → Сервер». С ADR-086 подписи, сделанные телефоном для того сервера (в том числе после ввода 24 слов: «добавить устройство», вход, «отключить устройство», «удалить аккаунт»), на настоящем сервере недействительны — они называют чужое имя.
20. **Превью в push (ADR-056).** Подписано ключом устройства отправителя и привязано к ключу доставки получателя; старше суток — не показывается. Пока у Apple не получено право `com.apple.developer.usernotifications.filtering`, push заблокированного появляется тихим «Новое сообщение» (без имени) до следующего запуска приложения. Закрытые ключи доставки на 5 недель лежат в общей с расширением Keychain-группе.

19. **Кто звонит — в приглашении (2026-10-16).** `CallInvite.caller_identity` — ключ звонящего, ставит сервер (он и так знает, кто звонит: это его соединение); участники группы видят звонящего в любом случае. Нужен, чтобы телефон отсеял групповой звонок от заблокированного. Подделать его звонящий не может — сервер затирает поле.
20. **Стикеры (ADR-049).** Каждый стикер при каждой отправке шифруется свежим ключом — сервер не видит, что в разных чатах шлют один и тот же стикер. Свой набор, которым поделились (из сообщения или кодом `sinhron-stickers:`), лежит на сервере одним зашифрованным объектом; ключ — только в сообщении или в коде (у кого код — тот откроет набор). Сервер видит, кто выгрузил объект и кто его скачал, — то есть может связать людей, открывших один набор. Импорт файлов — только локально; наборы Telegram приложение не скачивает. Файлы наборов на телефоне — AES-256-GCM, ключ в SQLCipher-базе.
21. **Секретные слова у Apple / Google и на листе (ADR-059).** Кнопка «Сохранить в связку ключей iCloud» (iOS) / «в менеджер паролей» (Android) кладёт 24 слова туда (iCloud Keychain — сквозное шифрование Apple, ключ — код телефона; Google Password Manager — шифрование Google, на Android 13 и старше через Google Play services; или другой выбранный провайдер). Кто получит доступ к его аккаунту Apple / Google **вместе** с кодом телефона (или разблокированный телефон), получит слова = аккаунт. Без синхронизации паролей в iCloud запись остаётся только на этом iPhone — приложение не может это проверить и говорит в подписи. Лист восстановления — PNG со словами и QR: временный файл удаляется, когда закрывается окно «Поделиться» (копию `share_plus` на Android — `cache/share_plus/` — через 5 минут, при запуске и при выходе; до 2026-11-04 она лежала до следующего «Поделиться», `storage-devices:7`), но копия остаётся там, куда его отправили (печать, «Файлы», мессенджер); предупреждение — на самом листе. С 2026-11-04 (ADR-085, `storage-devices:2`) на iOS это запись связки ключей самого приложения (`dev.sinhron.words`, синхронизируется через iCloud), а не пароль сайта: до этого слова были паролем сайта `SinhronPasswordDomain`, и страница этого домена (оператор, взлом VPS или домена) могла выманить их автозаполнением Safari. Старая запись переносится один раз («Вставить…» или «Перенести в связку ключей iCloud») и удаляется; пока человек этого не сделал, атака для его старой записи остаётся. Экран слов: Android — `FLAG_SECURE`; iPhone — слова закрыты, пока экран записывается или транслируется; снимок экрана на iPhone не запретить. «Скопировать» — iPhone: только этот телефон, буфер пустеет через 60 с; Android 13+: без превью и истории клавиатуры (`storage-devices:8`). **Открыто (аудит 2026-11b):** 24 слова показывались без Face ID через «Вставить из Паролей» (06/SEED-1) — _закрыто 2026-11-12 (0.12.0, запись 257): слова из связки ключей только после Face ID/кода_; слова сохранялись после создания аккаунта (06/SEED-2) — _при «Позже» теперь кладутся на телефон до создания аккаунта; остаток открыт (см. `docs/tech-debt.md` 2.68)_. На телефонах не проверено.
17. **«В сети / был(а)» (ADR-031).** Выключено по умолчанию. Если включено — уходит только контактам, сквозь MLS (действие `presence` в личных чатах); сервер не знает, кому статус виден, но по-прежнему видит время моих соединений (как и без этой функции) и всплеск маленьких сообщений в мои личные чаты при открытии приложения, а потом — по одному в каждый такой чат каждые 25 с, пока приложение на экране (запись 170; было раз в 5 мин). По этому ритму сервер может понять, что приложение на экране, — и раньше мог, теперь точнее; на iPhone он и так видит это по соединению, которое в фоне закрывается. Подделать статус может только сам собеседник. Выключение рассылает `hidden` — контакты стирают «был(а)»; изменённый клиент контакта может это проигнорировать.
21. **«Поделиться» в Sinhron (ADR-060).** Пока человек выбирает чат, присланное из другого приложения лежит открытым файлом: на iPhone — в App Group `group.com.sinhron.sinhron` (`FileProtectionType.complete` — закрыто, пока телефон заблокирован; вне резервных копий), на Android — в кэше приложения. Удаляется после отправки или отмены, забытое — через сутки. Расширение iPhone не держит ключей и не трогает базу. Android не берёт `file://` и адреса собственных провайдеров Sinhron — чужое приложение не подсунет «поделиться» нашими же файлами; ничего не уходит, пока человек сам не выбрал чат и не нажал «Отправить» (блокировка приложения закрывает и этот экран).

Файлы наборов на телефоне — AES-256-GCM, ключ в SQLCipher-базе.
21. **Стикерпаки из Telegram (ADR-062).** Телефон с Telegram не связывается: набор по ссылке берёт наш сервер ботом оператора (Bot API). **Telegram** видит: бот такого-то сервера (его IP) запросил набор X и его файлы, в такое-то время — не видит, кто из людей попросил. **Наш сервер** видит: аккаунт (подпись) попросил набор X — в момент запроса, для лимита; кэш (сутки) хранит только имя набора и файлы, журналы — ни имени набора, ни аккаунта. Скачанный набор на телефоне — обычный свой (зашифрован, п. 20). Токен бота — файл на хосте `/etc/sinhron/telegram/bot-token` (400, uid контейнера); кто получит root на сервере, получит и токен (бот может только читать публичные наборы — ущерб: от имени бота). В журналы токен не попадает (ошибки без URL). Чужой сервер Bot API (`SINHRON_TELEGRAM_API_URL`) видит то же, что Telegram, и может подсунуть другие файлы — приложение проверяет только формат по байтам и размер.
8. **Metadata at server.** Spec §13.1 perimeter — operator всё ещё видит social graph + timing + sizes. Mitigation = self-host или Tor relay (out of scope).
9. **Metadata at LiveKit.** LiveKit operator видит participant identity (JWT claim), call timing, packet sizes, IP. Self-host LiveKit рядом с sinhron-app (что мы и делаем) минимизирует cross-operator leak.
10. **Forward secrecy of pending_welcomes.** Welcome blobs sit в Postgres столько же, сколько сообщения — `SINHRON_MESSAGE_RETENTION_DAYS`, по умолчанию год (было 7 дней; запись 220: телефон без связи дольше недели терял приглашение и весь новый чат) (Risk #10). Окно утечки при взломе сервера стало длиннее — осознанный выбор владельца: «мы ничего толком не теряем». Сервер compromise during this window → новый member's first epoch keys могут утечь. Mitigation: client should rotate KeyPackage frequently.

12. ~~**Push payload содержит `group_id_hex` plaintext**~~ — закрыто 2026-10-13 (TD 2.7): payload несёт только unread count; Apple/Google не видят, какой чат активен.
13. **Media metadata (ADR-017).** Сервер видит размер каждого блоба с точностью до бакета Padmé (с 2026-10-13; превью — всегда 32 КиБ), время загрузки, загрузившее устройство (`uploaded_by_device`), моменты скачивания и кто скачивал (identity в заголовке). Не видит: содержимое, тип, имя файла, чат. Дедупликация по sha256 — оракул «такой блоб есть» для того, кто уже знает хеш. Скачать блоб может любой зарегистрированный identity, знающий sha256 (без ключа бесполезно).
15. **Link previews (ADR-018), если включены.** Превью строит **отправитель**: его устройство открывает страницу и видит его IP; получатели сайт не трогают. Только https, без IP-литералов/localhost/*.local, ≤3 редиректа с повторной проверкой, лимиты размеров, нейтральный User-Agent. Не закрыто: публичное DNS-имя, резолвящееся в приватный IP. Превью, URL которого нет в тексте, получатель отбрасывает (защита от подмены). По умолчанию выключено.
14. **Media plaintext on device (ADR-017).** Видео перед отправкой (2026-10-13): временный файл выбора и сжатая копия `video_compress` живут, пока клип читается в память, затем удаляются вместе с кэшем плагина; кадр-превью уходит только как зашифрованная миниатюра. Временные файлы при открытии/шаринге, записи голоса и выборе файлов живут секунды и удаляются, но на это время лежат в tmp приложения (защита iOS по умолчанию — до первой разблокировки). «Сохранить в Фото» и share sheet — явный экспорт за пределы Sinhron (видео в «Фото» — через временный файл в своей папке tmp, удаляется сразу после записи; 2026-10-18). Просмотрщик фото и видео (2026-10-18) держит всё в RAM: соседние фото и небольшие видео (< 16 МБ) расшифровываются заранее в тот же `MediaCache` (LRU 64 МБ), видео играет через `RamMediaServer` (127.0.0.1, случайный путь), сервер закрывается вместе со страницей. Голосовое при проигрывании отдаётся плееру через локальный HTTP-прокси `just_audio` на 127.0.0.1 со случайным портом — теоретически доступен другим процессам устройства на время воспроизведения.
16. **Порядок коммитов (ADR-022).** Сервер упорядочивает Commit'ы по заявленной клиентом эпохе (`commit_epoch`), не видя содержимого. С 2026-11-02 — только эпоха группы ровно; с 2026-11-04 (ADR-090) и новый чат начинается с эпохи, объявленной создателем (без «догона» до 100). С 2026-11-04 (ADR-092, запись 247) мусор на текущей эпохе чат больше не замораживает: сервер хранит каждый Commit и берёт Commit для эпохи от устройства, которое видело и не применило все Commit'ы этой эпохи после того, что привёл его туда (`Submit.parent_commit_id`, `refused_commit_ids`); телефоны берут первый годный. Сервер по-прежнему не видит содержимого Commit'а; узнаёт только, что устройство какой-то Commit не применило. Предел: Commit «на половину чата» (ключи пути годные одним, мусор другим) раскалывает чат — предел MLS против участника.
22. **Ответ из уведомления (ADR-066).** Ответ уходит обычным MLS-сообщением — ни Apple, ни Google, ни сервер нового не видят (сервер — как любое сообщение, плюс короткое фоновое подключение телефона). Набранный текст до отправки лежит на телефоне зашифрованным (Android — ключом Keystore в `SecureStore`, iPhone — в Keychain «только это устройство»), удаляется, как только приложение взяло его в чат. Ответить можно только на **разблокированном** телефоне (`authenticationRequired`) и **не при включённой блокировке приложения** (иначе ответ обошёл бы её); нет ответа при «Уведомления показывают: ничего», в запросах на переписку и чатах с заблокированными. Кто держит разблокированный телефон без блокировки приложения, может ответить — как и открыть приложение.
21. **Перенос и синхронизация моих устройств (ADR-064).** Вся история, контакты, стикерпаки и настройки идут через сервер **шифротекстом**: части и манифест — как медиа (свежий AES-256-GCM-ключ на каждую, размер по Padmé), ключ манифеста — только внутри MLS в группе, где нет никого, кроме моих устройств, и запечатан на мой ключ доставки; `Transfer` / `DeviceSync` принимаются только от меня и только в такой группе. Сервер видит: аккаунт выгрузил пачку блобов (суммарный объём ≈ размер истории), спросил `POST /v1/media/touch` про пачку хэшей (те же хэши, что видел бы при скачивании; заодно продлевает их хранение) и группа одного человека получила несколько MLS-сообщений — то есть «похоже на перенос», но не содержимое, не число чатов и не с кем. Кто владеет любым моим устройством, получает всё (как и раньше — устройство моё; против этого — отзыв, ADR-027). Потерянное старое устройство = переноса нет; с 2026-10-22 есть копия в облаке самого человека — п. 24 (ADR-073).
22. **Скоропортящиеся доставки (tech-debt 2.53, 2026-10-19).** «В сети» и «печатает» идут с `drop_after_secs` = 120 с: сервер удаляет их, если получатель не забрал. Сервер видит этот флаг, то есть отличает их от настоящих сообщений и квитанций (раньше — только по размеру и ритму); чат, отправитель (на анонимном пути) и содержимое скрыты по-прежнему. Флаг ставит отправитель; подделанный флаг вредит только его собственной доставке.
22. **Блокировка = отзыв ключа (ADR-071) — что видит сервер.** До: ничего о блокировках, но и телефон будился заблокированным. После: сервер хранит набор хэшей ключей доступа человека (число ≈ собеседники + он сам) и флаг «отозван» у части из них (число ≈ заблокированные), время каждого изменения (момент решения — с часов устройства) и что человек перешёл на ключи по собеседнику. **Не видит**, чей хэш: ключ передаётся внутри MLS, на WS-пути ключ не передаётся. **Видит в момент звонка:** звонящий вошёл, приглашение несёт его ключи — сервер сам решает «проглотить» и, значит, знает, что вызываемый его заблокировал; обычный сервер это никуда не пишет (в журнале число приглашённых — как без блокировки), но изменённый сервер может запомнить, какой ключ показал звонящий, и потом увидеть отзыв этого ключа. Заблокированный видит тот же ответ «принято», что и раньше (отличить можно разве что по времени ответа — без записи в базу он чуть быстрее). Дополнено (status 177): push о запросе сервер шлёт и заблокированному отправителю (он неотличим от незнакомого) — Apple видит фоновый push с непрочитываемым превью в момент запроса, Google / ntfy — шифротекст того же размера, что у сообщения; что показать, решает телефон. Ключ звонящего в push Android — только внутри шифрования ключом телефона (сервер его и так знает). Своих устройств владельцу надо обновить все: старое моё устройство раздаёт прежний общий ключ, и сообщения собеседников мне идут без push, пока новое не раздаст ключи снова.
23. **DNS-over-HTTPS (ADR-072) — кто узнаёт имя сервера.** Пока системный ответ DNS проходит проверку (наш сертификат), всё как раньше. Если не проходит (подмена провайдером, блокировка), телефон спрашивает адрес у **Cloudflare** (`1.1.1.1`), а если тот не ответил — у **Google** (`8.8.8.8`): они видят имя нашего хоста (API, `livekit.`, `turn.`), время и IP телефона — то, что раньше видел только DNS провайдера. Содержимого и с кем переписка — нет. Проверка адреса (TLS-рукопожатие) уходит туда же, куда ушло бы само соединение. Провайдер видит, что телефон обращается к 1.1.1.1 / 8.8.8.8 по HTTPS. Проверенные адреса хранятся в зашифрованной базе (`settings.net_dns_cache`). При SOCKS-прокси (Tor) ничего этого нет — имя резолвит прокси.

23. **«Сообщить о проблеме» (status 190, 2026-10-22).** Журнал приложения и системной части (push, звонки) за час лежит на телефоне открытым текстом (`Application Support/diag.log`, `diag-native.log`, ≤ 512 + 128 КБ; Android — в личной папке приложения, iPhone — в песочнице, обе — под шифрованием телефона). В нём нет текста сообщений, имён, ключей и push-токенов: только события, время, ошибки, начала id (6 знаков, `scrubDiagLine`) — но по нему видно, когда приложение было открыто, когда звонили и с какой сетью (VPN, сервер). Наружу уходит **только по нажатию человека** и туда, куда он сам выберет в «Поделиться»: в Sinhron — сквозным шифрованием, в Telegram / почту — как обычный файл этим сервисам. Сервер Sinhron отчётов не получает. С 2026-11-04 (`storage-devices:15`) журнал стирается при выходе, удалении аккаунта и «Стереть и начать заново»; на iPhone оба файла не попадают в бэкап iCloud (с запуска после их появления).
24. **Копия переписки в iCloud / Google Диске (ADR-073, 2026-10-22).** Вся история, контакты, настройки, стикерпаки и медиа уходят в облако человека **шифротекстом**: части и медиа — как в переносе ADR-064 (свежий AES-256-GCM на каждую часть, Padmé), ключ манифеста — в `root.sinhron` под ключом копии (HKDF из ключа копии состояния, из 24 слов). **Apple / Google видят:** число и размеры файлов, время загрузок и удалений, что это Sinhron, 16-значные метки устройств (хэш сертификата / ключа личности — без смысла для них). **Не видят:** содержимое, людей, чаты, число сообщений (оно внутри корня). Кто получит доступ к облаку **и** 24 словам (например, в «Паролях» того же Apple ID — п. 21), получит всю переписку. **Связанные устройства теперь хранят ключ копии** в своём пакете (Keychain / Keystore): кто вынет его с устройства и войдёт в облако человека — прочтёт копию, но с самого устройства он и так читает всё; ключ личности и ключ серверной копии состояния на связанные устройства не попадают. **После отключения устройства** (ADR-084, 2026-11-04) копии делаются ключом нового поколения из свежих случайных байт, которого у отключённого нет: оно открывает только копии, сделанные до отключения (и копии моего устройства, которое ещё не узнало о новом поколении). Корни других аккаунтов в той же папке (общий Apple ID) не открываются и не трогаются. Временные файлы копии и восстановления — в tmp приложения, только шифротекст, удаляются после загрузки / в конце. Наш сервер в копии не участвует. **Откат копии** (ADR-090, 2026-11-04, storage-devices:14): кто управляет облаком, мог вернуть старую копию, и новый телефон брал её как самую свежую. Теперь сервер хранит время самой новой копии устройств аккаунта (по облаку, `POST /v1/backup-mark`, подпись устройства), и перед восстановлением телефон предупреждает, если в облаке нет копии такой свежести. Откат незаметно — только облако **и** наш сервер вместе; сервер узнаёт, когда человек делает копии. **Копия не подписана устройством (аудит 2026-11b, BKP-1):** корень копии не подписан устройством; тот, кто держал связанный пакет устройства **и** может писать в облако владельца, подкладывает копию, которую откроют 24 слова. _Смягчено 2026-11-12 (ADR-105): после восстановления делается новое поколение ключей, «проверено» и часы из копии не берутся, корни «из будущего» отбрасываются._ Не закрыто: поддельные сообщения и имена в восстановленной истории.
25. **Собеседники добавляют мой новый телефон (ADR-074, 2026-10-23).** Любой участник чата добавляет новые устройства других участников по списку сервера. **Сервер не может** добавить так нового человека или подменить устройство: KeyPackage принимается, только если в нём действительный сертификат устройства именно того человека, для которого его просили, лист подписан ключом из этого сертификата (с записи 225; раньше чужой сертификат или ключ личности на ключе сервера проходили), и этот человек уже в чате (раньше мои устройства добавляли «моё новое устройство» без проверки, что оно моё, — сервер мог подсунуть постороннего во все мои чаты; закрыто). **Сервер может** не показать устройство (не добавят) или показать отозванное как активное (собеседники добавят его обратно — тот же уровень доверия к списку устройств, что и раньше у моих устройств; отзыв — на сервере). Видит, что участник добавил устройство другого участника. Каждый открытый телефон раз в 10 минут спрашивает список устройств собеседников (`GET /v1/devices`) — сервер видит, чьи устройства спрашивают, то есть кто с кем в чатах (это он и так знает по группам). Запас из 20 KeyPackage на устройство — только больше записей в таблице. _Закрыто 2026-11-12 для СВОИХ устройств (ADR-104): телефон помнит отключённые им устройства (`device_revoked:<ключ>`, синхронизируется между своими устройствами) и не возвращает их в чаты, что бы ни показал сервер._ Остаётся: телефон, вошедший по 24 словам на пустое место, списка не знает, пока его не пришлёт другое своё устройство; собеседники полагаются на подписанный отзыв (ADR-075).
26. **Карточка чата и отключение с подписью (ADR-075, 2026-10-23).** Сервер хранит GroupInfo каждого чата (публичные ключи устройств, внешний ключ эпохи) — состав групп он и так знает (`group_members`), содержимого и имён в карточке нет. Карточку отдают только устройству человека, который в чате (или чьё отключённое устройство там было); войти по ней участники пускают только устройство человека, у которого уже есть лист — постороннего не пустит ни его телефон, ни телефоны участников. Отзыв устройства теперь подписан ключом аккаунта, и собеседники убирают отключённый телефон из чатов, только проверив подпись сами — сервер не может «отключить» чужое устройство. Предел: сервер вместе с украденным отключённым телефоном мог бы провести его обратно по карточке; при следующей синхронизации телефоны собеседников снова уберут лист с подписанным отзывом (кроме последнего листа человека). Отключённое первое устройство не входит по WS (403); кто вытащил с него сам ключ аккаунта — тот и есть аккаунт (как и раньше). С 2026-11-04 (ADR-090) первая карточка эпохи остаётся, заменить её может только устройство, чей Commit сделал эпоху (участник, сделавший пустой Commit, — может). С ADR-092 автор эпохи — устройство последнего взятого сервером Commit'а; после Commit'а, который телефон не применил, он делает свой пустой Commit при открытии — эпоха и карточка снова у честного участника. Окно остаётся: новый телефон, вошедший по карточке участника-злоумышленника до этого, попадёт в его копию чата. С 2026-11-06 (ADR-093) у каждого устройства своя карточка, и новый телефон берёт ту, что оставил его человек или большинство людей (одно устройство — не голос, один человек — один); остаётся ничья «одна честная против его» сразу после мусорного Commit'а, до лечения. _Изменено 2026-11-12 (ADR-100, второй аудит 2026-11b): правило «ту, что оставил его человек или большинство» больше не действует — новый телефон входит **только по карточке, подписанной другим устройством того же человека**; карточки других людей не используются. Поддельная карточка сервера (своя группа сервера с настоящим KeyPackage жертвы) раньше давала серверу читать и подделывать сообщения восстановленного телефона — это был обход сквозного шифрования, а не «отказ в обслуживании», как было записано; закрыто. Окно «вошёл по карточке участника-злоумышленника» закрыто тем же. Срок действия KeyPackage при входе в чат для уже состоящих участников не проверяется (CM-04); срок нового пакета проверяется при добавлении._ **Открыто после аудита 2026-11b:** (а) CM-02 — телефон, восстановленный с нуля, не знает последней эпохи чата; сервер в сговоре с удалённым из чата человеком может отдать подлинную, но старую карточку МОЕГО устройства — тогда удалённый читает сообщения нового телефона. Телефон с мёртвой копией чата старую карточку не возьмёт. Лечение — эпоха чата в резервной копии. (б) CM-12 — предел «украденный отключённый телефон + сервер» остаётся: карточка, подписанная украденным устройством, для нового телефона выглядит своей; телефоны не помнят подписанных отзывов. (в) Для собственных устройств человека сервер, не показав устройство в списке, всё ещё заставляет телефон убрать его из чатов (PAIR-3 / DEV-5, не закрыто) — «сервер не может отключить чужое устройство» верно для устройств собеседников. (г) Не трогалось (low для семьи): CM-10 (запрос на переписку обходится приглашением двух моих устройств), CM-11 (Welcome с номером известного чата на восстановленном телефоне), CM-13 (сервер), CM-14 (message_id вне шифрования), CM-15 (переименование группы любым участником, цитата), CM-16 (тихое пересоздание базы ключей).

27. **Администратор сервера (ADR-077, 2026-10-24).** Если оператор назначил администраторов (`SINHRON_ADMIN_IDENTITIES`), сервер **записывает** к жалобе IP жалующегося и последний IP того, на кого жалоба (стираются через 30 дней), держит в памяти последний IP каждого аккаунта — адрес его последнего входа по WS (не на диск, до перезапуска), и пишет администраторам служебные уведомления (тревоги о нагрузке, жалобы с ключами и IP) — в базе открытым текстом, 30 дней. Кто получит базу, узнает IP жалующихся и нарушителей за 30 дней. С 216 (урезано) сервер больше **не** считает трафик по аккаунтам и запросы по IP. Без администратора ничего этого нет. Уведомления отдаются только устройству человека из списка (подпись), остальным — 403. IP берётся из `X-Forwarded-For` (последний адрес): за Caddy он настоящий, без прокси — подделывается клиентом. Push администратору — обычный «новое сообщение» без текста.

- **Этот документ** обновляется при каждом изменении threat surface (new endpoint, new feature, new dependency with crypto impact).

- **Ad-hoc review** при появлении relevant CVE в openmls / rustls / SQLCipher / OpenSSL.
- **2026-11 — аудит-2**, двенадцать областей, свод в `docs/security-audit-2026-11b/README.md`; восемь областей остались черновиками — их находки не перепроверены.
